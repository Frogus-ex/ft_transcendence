# Description:
## ft_transcendence

This project is a full-stack cryptocurrency paper trading platform inspired by Binance. It recreates the core experience of a real-time trading dashboard on a smaller scale, using live market data from Binance APIs and a simplified interface for monitoring prices, chart trends, and market activity. Users start with a virtual cash balance, place simulated buy/sell orders at the live price and follow their portfolio without risking real money.

The platform is designed to combine:
- real-time market data ingestion;
- historical OHLC candle storage;
- a backend API for chart, watchlist, portfolio and order queries;
- WebSocket-based streaming for live updates;feat(markets): responsive layout for the markets page
- a persistent PostgreSQL database for structured market and user data;
- user management (authentication, 2FA, friends, chat, API keys, GDPR tools);
- a monitoring stack (Prometheus / Grafana) with alerting.

# Instructions:

This project requires a working container environment with Make and a compatible runtime such as Docker or Podman (the Makefile uses `podman-compose`). The repository also relies on environment variables and generated secrets stored in the root `secrets` directory.

1. Run the following command from the repository root:
   ```bash
   make
   ```
   This command copies `.env.example` to `.env` (if missing), generates the required secrets, sets execution permissions, pulls the images and starts the full project stack.
2. Open the application: **https://localhost:8443** (self-signed certificate: accept the browser warning). `http://localhost:8080` redirects to HTTPS.
3. To stop all containers without deleting persistent volumes:
   ```bash
   make down
   ```
4. To reset the environment completely, including volumes and generated secrets:
   ```bash
   make fclean
   ```
5. To rebuild and relaunch the project from scratch:
   ```bash
   make re
   ```
6. To inspect the logs of all services in real time:
   ```bash
   make logs
   ```
7. To view a recent log window for the current stack:
   ```bash
   make fixlog
   ```
8. To follow the logs of a specific container:
   ```bash
   podman logs -f <container_name>
   ```
9. To check the status of the running containers:
   ```bash
   make ps
   ```

Example environment file (`.env.example`, copied to `.env` by `make`):
```.env
# Postgres Admin
POSTGRES_ADMIN_USER=transcendence_user
POSTGRES_DB=transcendence_db
POSTGRES_HOST=postgres
POSTGRES_PORT=5432

# Postgres Ingestion User
POSTGRES_INGEST_USER=ingest_user

# Postgres Read-Only User
POSTGRES_READONLY_USER=reader_user

# Postgres Application User
POSTGRES_APP_USER=app_user

REDIS_HOST=redis
REDIS_PORT=6379

# SMTP for GDPR confirmation emails (leave SMTP_HOST empty to disable sending)
SMTP_HOST=
SMTP_PORT=587
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=no-reply@ft-transcendence.local
SMTP_STARTTLS=true
```

Passwords and the JWT secret are **not** stored in `.env`: they are generated by `make` as Docker/Podman secrets (`postgres_*_password`, `redis_password`, `jwt_secret`, `grafana_admin_password`, …).

Services exposed by the stack: nginx (HTTPS 8443), React frontend, FastAPI API server, data-ingestion pipeline, Celery worker + beat, PostgreSQL, Redis, Prometheus, Grafana and the exporters (node, postgres, redis, celery).

**Known limitations**
- There is no migration system: tables are created at API startup (`create_all`) and never altered. After pulling a change that adds a column, run `make re` (wipes the data).
- GDPR confirmation e-mails are only sent if an SMTP server is configured in `.env` (`SMTP_HOST`). Without it the actions still work, no e-mail is sent.
- Two-factor secrets are stored in the database as plain text.

# Technical Stack:
## Data Ingestion & API Server Backend
- PostgreSQL: used for reliable persistence of historical OHLC market data and structured queries.
- SQLAlchemy: chosen to manage database access in Python with a clean ORM layer instead of writing raw SQL throughout the application.
- Redis / RedisTimeSeries: used for low-latency live storage, cache management, and time-bucket calculations for real-time market data.
- Celery: used for asynchronous task processing and periodic aggregation jobs without blocking the real-time ingestion flow.
- FastAPI: used for building a lightweight and high-performance REST API layer with strong request validation.
- SlowAPI: used to enforce rate limiting and protect the API from excessive request bursts.

This backend architecture was selected to balance responsiveness, reliability, and maintainability. Redis is ideal for live market updates and fast calculations, while PostgreSQL is better suited for persistent historical records and structured query access. Celery allows time-consuming tasks to be offloaded from the core ingestion path, and FastAPI provides a clean interface for both HTTP and WebSocket-based data delivery.

## Frontend
- React + TypeScript + Vite: component-based SPA with fast builds and typed props.
- Tailwind CSS v4: utility-first styling and a shared set of design tokens; responsive layouts (mobile / tablet / desktop).
- React Router: client-side routing with a `PrivateRoute` guard for authenticated pages.
- React Context (`AuthContext`, `PortfolioContext`, `MarketContext`): authentication state, portfolio and market selection.
- lightweight-charts (TradingView): candlestick charts fed by the REST API and the WebSocket stream.
- react-qr-code: QR code display for two-factor authentication setup.

## User Management & Security
- JWT (HS256) access tokens (20 min) and short-lived `2fa_pending` tokens (5 min) that cannot be used as sessions.
- Passwords hashed before storage; API keys (`tk_…`) stored as SHA-256 hashes.
- TOTP two-factor authentication (pyotp).
- SMTP mailer for GDPR confirmation e-mails.

## Infrastructure & Monitoring
- nginx as HTTPS reverse proxy (self-signed certificate, HTTP→HTTPS redirect).
- Podman Compose orchestrated by a Makefile; secrets generated at setup time.
- Prometheus (8 scrape jobs) + Grafana (6 provisioned dashboards) + 4 alert rules, with node, postgres, redis and celery exporters.

# Database Schema:
## Data Ingestion Database

The project uses the `transcendence_db` PostgreSQL database, with the `market_candles` table storing the OHLC market data generated by the ingestion pipeline. This table is populated from the Redis Time Series flow and periodically flushed to PostgreSQL by Celery tasks.

Main fields:
- `symbol`: the cryptocurrency pair, such as `BTCUSDT`;
- `interval`: the time bucket, such as `1m`, `15m`, or `1h`;
- `time`: the timestamp associated with the candle window;
- `open`: the opening price of the period;
- `high`: the highest price reached during the period;
- `low`: the lowest price reached during the period;
- `close`: the closing price of the period;
- `volume`: the traded quantity for that interval.

The table includes:
- a unique constraint on `(symbol, interval, time)` to avoid duplicate candle entries;
- an index on `(symbol, time DESC)` to optimize historical queries;
- an upsert strategy for conflict handling when the same candle would be written again.

Access is split across four PostgreSQL roles:
- Admin: full database privileges, used for schema creation and maintenance.
- Ingest User: restricted to the insert/update operations required by the ingestion service.
- Reader User: read-only access for safe historical queries and inspection.
- App User: least-privilege account used by the API server for the application tables.

See [backend/data-ingestion/DOC.md](backend/data-ingestion/DOC.md) for more details.

## Application Database

The API server creates the following tables at startup (SQLAlchemy models in `backend/api-server/src/database/models.py`):

| Table | Purpose | Main fields |
|---|---|---|
| `users` | Accounts | `id`, `email` (unique), `username`, `password_hash`, `two_fa_enabled`, `totp_secret`, `avatar_url`, `created_at` |
| `portfolio` | One portfolio per user | `user_id` (FK), `cash_balance` (default 100000), `positions` (JSON text, default `"[]"`) |
| `orders` | Simulated buy/sell orders | `id`, `user_id` (FK), `symbol`, `side`, `quantity`, `price`, `created_at` |
| `api_keys` | Public API keys | `id`, `user_id` (FK), `name`, `key_hash` (SHA-256), `created_at`, `last_used_at` |
| `friends` | Friendships between users | `user_id`, `friend_id`, `status` |
| `messages` | Chat messages between friends | `sender_id`, `receiver_id`, `content`, `created_at` |
| `market_candles` | OHLC history (see above) | see above |

Relations: `portfolio`, `orders` and `api_keys` reference `users` (deleting a user removes their data, which is used by the GDPR "delete my account" feature); `friends` and `messages` link two users.


# Features List:

- Data Ingestion *(by gwen)*:
  - Connects to the Binance WebSocket streams and retrieves live market events.
  - Validates and normalizes the incoming payloads to keep only the data needed for the platform.
